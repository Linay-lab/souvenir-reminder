# 第二階段：帳號與訪客資料隔離

## 範圍與基礎
GitHub `Linay-lab/souvenir-reminder` main：`670066736712746a25f3daf11a4cec2c8f0f4700`，已確認包含上一階段 `6700667`。獨立分支 `fix/auth-guest-isolation-stage2`。沿用先前候選的 Auth 初始化、訪客資料驗證、跨分頁帳號切換及讀取錯誤處理；未套用候選的 revision、登入回呼或重設密碼修改。

## A. 修改摘要
- 確認 getUser 後才決定雲端或訪客模式；等待、錯誤與已載入狀態分開。
- 登出／不同帳號事件先使請求世代失效、取消進行中的資料請求，清除畫面、旅行選取與編輯暫存，再跳轉重新確認身分；忽略已開始切換後的重複事件，避免雙重導向。
- 同帳號 SIGNED_IN／TOKEN_REFRESHED 不重載頁面、不清除草稿。
- 訪客三個既有儲存鍵只在確認為訪客且完成合法資料載入後才可持久化；不清空 localStorage，不自動匯入或合併雲端資料。
- 旅行／商品讀取錯誤顯示明確錯誤與重新載入入口；重新載入會再次 getUser，讀取失敗不會觸發空清單寫入。
- 讀取與既有寫入加上 AbortController、帳號／世代有效性檢查。既有商品更新、刪除再限制當前 trip_id，旅行更新限制 owner_id；不新增 revision 條件或資料庫欄位。
- 保留原有配色、頁面與表單設計；只增加必要的錯誤、載入、操作中禁用提示。將既有狀態宣告集中，供 Auth 初始化與切換清理使用，未抽換整個架構。

- `app/page.tsx`：唯一執行期程式改動；帳號初始化、資料隔離、請求失效與讀取重試。

- `docs/STAGE2-AUTH-ISOLATION.md`：本報告。

## D. 安全界線與未驗證事項
- 所有驗收使用真實 Chromium 與既有 Supabase SDK，但 Auth／REST 回應皆為合成資料；不是正式 Supabase 或實體手機驗收。沒有寄信、讀取真實使用者紀錄或執行資料庫操作。
- 不修改資料庫結構、RLS、Storage、授權及套件版本；不使用 Service Role，不包含真實 JWT、密碼或金鑰。
- AbortController 只能取消客戶端等待／盡力取消傳輸，無法撤回伺服器已接受的寫入；伺服器權限仍須由既有 RLS 執行。舊回應不再更新新帳號畫面，取消不會刪除雲端資料。
- 舊版本若已把雲端資料寫入沒有帳號標記的訪客儲存，無法可靠區分它與合法訪客資料；本次不猜測、不清空歷史資料，只防止後續污染。共用裝置既有紀錄需另行確認。
- 此修正不處理多人同時編輯的版本衝突，也不補上其他階段發現的資料庫政策、密碼保護或重設連結問題；未宣稱整個產品已完成安全驗收。
- 跨分頁使用 Supabase SDK 的 Auth 事件；瀏覽器封鎖相關通道的特殊環境未驗證。iOS/WebKit、Android 實機與真實服務均未驗證。
- 測試使用既有套件，無新增安裝。共用套件目錄在本環境不被 Turbopack 接受，因此隔離開發測試改用既有 Webpack 模式，未改 next.config.ts。
